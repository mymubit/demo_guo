# ScriptForge V6 产品与开发计划

## 1. 计划目标

本计划以 `short-drama-script-platform.html` 的产品原型为交互参考，以 `drama-skills/v6` 为唯一 AI 能力和业务契约来源，重新设计一个面向单人短剧创作者的可商业化产品。

产品不是 V6 技能管理后台，也不是把 9 个 operation 逐个做成菜单。用户看到的是短剧创作任务，系统在后台把任务映射到 V6 operation、版本化产物、验证器和调用账本。

### 1.1 核心用户

- 当前：单人短剧编剧/主创，重度使用，优先解决创作效率、连续性和质量问题。
- 后续验证：小型编剧工作室的单项目主创。
- 当前不做：多人实时协作、团队权限、会员计费、交易市场、模板 UGC、开放 API。

### 1.2 核心价值

1. 从一个创意或待改编故事，逐步形成可交付短剧剧本。
2. 所有 AI 产出可编辑、可比较、可拒绝、可回退。
3. 人物、世界、情绪、伏笔和相邻集上下文保持一致。
4. 质量评分和平台合规相互独立，问题可定位到具体集和场景。
5. 每一次 LLM 参与都可从用户动作追溯到输入、调用、验证和产物版本。

## 2. 原型取舍

### 2.1 保留并重构

| 原型设计 | V6 产品化方式 |
| --- | --- |
| 项目列表首页 | 项目卡片、当前进度、下一步、最近编辑 |
| 新建项目引导 | 对应 `create-project-brief`，支持原创/改编两条入口 |
| 人物管理 | 作为“故事设定”内的人物系统视图，由 `compose-story-bible` 生成 |
| 场景/分集管理 | 作为“分集规划”和“剧本创作”两个工作区 |
| 三栏编辑器 | 左侧分集/场景，中间正文，右侧上下文相关 AI 工具 |
| AI 创作助手 | 仅展示当前上下文可用动作，不做通用聊天框 |
| 剧本诊断 | 合并质量评分、合规检查、问题接受和定向修订 |
| 自动保存与版本 | 每次人工编辑保存草稿；AI 提交形成正式版本 |
| Word/PDF 导出 | 由 `prepare-delivery` 形成交付包后导出 |

### 2.2 当前明确不做

- 会员、积分、支付和套餐。
- 多人实时协作、评论、团队权限。
- 剧本交易、课程、社区和模板市场。
- 通用素材库、公共金句库、随机灵感库。
- 面向普通用户的规则、技能、模型配置页面。
- 将 operation graph、artifact key、prompt injection 等内部术语暴露给创作者。
- 第三阶段的商业化基础设施；第三阶段只做数据看板和创作分析。

## 3. 信息架构

### 3.1 全局导航

全局只保留三个一级入口：

1. **我的项目**：项目列表、新建项目、归档项目。
2. **独立审稿**：上传或粘贴外部剧本，执行质量与合规检查。
3. **创作分析**：第三阶段启用；第一、二阶段不显示空入口。

用户头像菜单包含账号、安全、模型连通状态和退出。模型供应商、规则版本和技能装配属于管理员内部页面，不进入创作者导航。

### 3.2 项目内导航

| 页面 | 用户问题 | V6 产物/operation |
| --- | --- | --- |
| 项目概览 | 现在做到哪，下一步是什么？ | 聚合全部产物和运行状态 |
| 创作定位 | 这部剧写给谁，卖点和边界是什么？ | `project_brief` / `create-project-brief` |
| 故事设定 | 人物、世界、关系、情绪和原创边界是什么？ | `story_bible`、`character_system`、`world_system`、`emotion_system`、`originality_report` |
| 分集规划 | 每集发生什么，钩子、情绪、伏笔、付费点怎么分布？ | `episode_plan` / design + revise |
| 剧本创作 | 如何写、改和管理每集正文？ | `episode_scripts`、`memory_checkpoint` / write + revise |
| 审稿修订 | 哪些问题必须改，改完是否通过？ | `quality_report`、`compliance_report` / score + compliance + revise |
| 制作交付 | 是否具备拍摄和发布条件，交付哪些文件？ | `production_package` / prepare-delivery |

“版本历史”和“运行详情”不作为一级页面，分别从产物版本和具体 AI 任务进入。

## 4. 关键用户流程

### 4.1 新建项目

1. 选择创作来源：原创构思或已有故事改编。
2. 填写创作核心：核心创意/原故事、受众、目标平台、参考作品。
3. 确认规模：集数、单集时长、单批生成集数、规划深度。
4. 确认边界：必须保留、必须修改、避免事项、制作规模。
5. 系统执行 `create-project-brief`，展示候选项目定位。
6. 用户可以直接编辑、重新生成或确认采用；确认后产生 `project_brief v1`。

不得在建项表单中一次暴露全部 V6 参数。质量、交付等高级设置使用默认值，之后可在对应页面调整。

### 4.2 从定位到故事设定

1. 项目概览提示“完善故事设定”。
2. 用户补充故事方向、角色要求、世界要求和硬约束。
3. `compose-story-bible` 生成一组原子提交：故事蓝图、人物系统、世界系统、情绪系统、原创性报告。
4. 页面按标签展示，不向用户显示五份 JSON。
5. 用户可锁定人物核心动机、结局方向、世界规则等不可破坏项。
6. 确认后整组产物原子提交，避免部分成功。

### 4.3 分集规划

1. 用户选择总集数、时长和规划要求。
2. `design-episode-plan` 生成全剧分集卡片。
3. 默认使用卡片/表格视图，支持阶段折叠和集数区间筛选。
4. 单集卡展示目标、冲突、转折、结尾钩子、情绪值、伏笔/回收和付费点。
5. 用户选择部分集数提出调整，调用 `revise-episode-plan`，不得重写全剧。
6. 修改前展示影响范围：会导致哪些已写剧本、报告和交付包过期。

### 4.4 剧本创作编辑器

桌面端采用原型的三栏结构：

- 左栏：分集树、场景列表、完成状态、字数和审稿状态。
- 中栏：专业短剧正文编辑器，支持场景标题、动作、人物、提示语和对白结构。
- 右栏：仅展示与当前集/选中文本相关的 AI 动作和上下文信息。

核心动作：

- 批量写第 N-M 集：调用 `write-episodes`。
- 续写当前场景：作为受控的写作子命令，仍走当前集候选/验证/提交链。
- 重写选中场景：必须填写修改目标和保留项。
- 对白优化：调用 dialogue advisory，只提供建议，不直接覆盖正文。
- 查看依据：显示当前集引用的项目定位、人物规则、分集卡和相邻集记忆。

所有 AI 改写先进入候选区，用户通过左右差异比较决定采用；不允许流式输出直接覆盖已保存正文。

### 4.5 审稿与修订

1. 用户选择剧本版本和集数范围。
2. 质量评分与合规检查可并行执行，但生成两份独立报告。
3. 质量页面顶部展示发布结论，不先展示十几个指标。
4. 问题按“必须修改、建议修改、提示”分组，并定位到集/场景/证据文本。
5. 用户逐条接受需要处理的问题，可补充修订要求和必须保留内容。
6. `revise-script` 只处理已接受问题和选定集数。
7. 修订后原报告变为“基于旧版本”，自动提示重新评分和合规检查。
8. 双报告通过后解锁制作交付。

### 4.6 制作交付

1. 用户选择目标平台和交付范围。
2. 系统检查质量、合规、原创性、制作可行性和预算来源。
3. 阻断项必须在页面顶部明确解释，不允许绕过。
4. `prepare-delivery` 生成制作交付包。
5. 支持导出剧本正文、人物小传、分集表、制作提示、预算摘要和发行检查表。

## 5. 页面设计规格

### 5.1 我的项目

- 顶部：页面标题、搜索、新建项目。
- 项目卡：封面色块、项目名、题材、集数、当前阶段、完成百分比、下一步。
- 最近项目优先；支持列表/卡片切换。
- 空状态直接提供“原创项目”和“改编项目”两个入口。
- 不展示运行次数、模型、技能版本、artifact 数量等技术指标。

### 5.2 项目概览

- 第一屏：项目名、当前状态、主要下一步按钮。
- 创作进度：定位、设定、规划、正文、审稿、交付六个业务阶段。
- 待处理事项：失败任务、过期内容、未接受问题、需要复核的版本。
- 最近内容：最近编辑的集数和产物。
- 运行详情只在错误或任务展开时出现。

### 5.3 创作定位

- 左侧为项目定位表单，右侧为当前已确认项目简报。
- 必须保留/必须修改/避免事项使用结构化标签编辑器。
- 重新生成时显示会失效的下游内容并二次确认。

### 5.4 故事设定

- 标签：故事蓝图、人物、人物关系、世界规则、情绪曲线、原创性。
- 人物页沿用原型的主从布局：人物列表 + 人物详情。
- 世界规则和不可破坏约束支持锁定。
- 情绪曲线提供全剧趋势可视化，但数据来自 `emotion_system`。

### 5.5 分集规划

- 视图：分集卡、紧凑表格、情绪/钩子分析。
- 支持按故事阶段、集数范围、问题状态筛选。
- 批量选择后可以请求局部调整。
- 卡片编辑保留字段级变更，提交时形成新计划版本。

### 5.6 剧本编辑器

- 使用 Tiptap/ProseMirror 定义结构化节点，不使用普通 textarea 存储整集。
- 场景、人物、对白和动作必须有稳定 ID，供报告精确引用。
- 自动保存草稿与正式版本分离。
- AI 工具是上下文动作菜单，不是常驻聊天机器人。
- 移动端不承诺完整编辑能力；提供阅读、审稿和轻量修改。

### 5.7 审稿修订

- 顶部：版本、范围、质量结论、合规结论、是否可交付。
- 中部：问题列表与正文定位双栏联动。
- 右侧抽屉：问题证据、修改建议、接受/忽略、补充要求。
- 支持一次选择多个问题生成修订方案。

### 5.8 运行详情

- 从具体任务进入，不作为创作者主导航。
- 默认展示：谁发起、做了什么、结果版本、耗时、失败原因。
- 高级标签：命令、计划、模型调用、Prompt、响应、验证、变更集、影响计划、提交。
- 每条 LLM 调用记录模型、参数、输入、输出、token、耗时、错误和注入清单。

## 6. V6 产品映射

| 用户动作 | V6 operation | 前置 | 写入 | UI 提交策略 |
| --- | --- | --- | --- | --- |
| 生成创作定位 | create-project-brief | 创作请求/项目设置 | project_brief | 候选确认后提交 |
| 生成故事设定 | compose-story-bible | project_brief | bible + character + world + emotion + originality | 多产物原子提交 |
| 生成全剧规划 | design-episode-plan | brief + bible | episode_plan | 全剧候选提交 |
| 调整部分分集 | revise-episode-plan | episode_plan | episode_plan | 范围化 diff 提交 |
| 写指定集数 | write-episodes | brief + bible + plan | scripts + checkpoint | 分批原子提交 |
| 质量评分 | score-script | 指定剧本版本 | quality_report | 报告直接提交，不改正文 |
| 合规审查 | check-compliance | 剧本 + 已验证政策 | compliance_report | 报告直接提交，不改正文 |
| 按问题修订 | revise-script | 已接受问题 + 剧本版本 | scripts + checkpoint | diff 确认后提交 |
| 生成交付包 | prepare-delivery | 双报告通过 + 原创性 | production_package | 通过门禁后提交 |

统一事务阶段：`command -> plan -> execution_pack -> candidate -> validation -> change_set -> impact_plan -> commit`。UI 默认只展示用户需要理解的阶段，高级运行详情保留完整证据。

## 7. 后端领域设计

### 7.1 核心模型

- `Project`：项目元数据、入口类型、当前设置版本。
- `ProjectSettingsRevision`：不可变项目设置历史。
- `ArtifactVersion`：统一存储所有 V6 产物版本、schema 版本、状态和来源运行。
- `ArtifactDraft`：人工自动保存草稿，不进入正式依赖图。
- `OperationRun`：一次用户操作的事务主记录。
- `OperationStageRecord`：八阶段状态、输入摘要、开始/结束时间和错误。
- `LlmCall`：完整模型调用证据。
- `CandidateChangeSet`：候选产物、结构差异、语义差异和影响范围。
- `QualityFinding`：从报告标准化出的可接受问题，包含证据定位和处理状态。
- `ContentLock`：用户锁定的字段、人物规则、场景或文本范围。
- `ExportPackage`：交付包文件与生成来源。
- `UsageEvent`：第三阶段分析所需的产品事件，从第一阶段开始采集。

不得继续以 `settings`/`metadata` JSON 拼装全部页面。结构稳定且参与查询、状态机或关联的字段必须建模；V6 artifact payload 仍按 schema 版本保存在 JSONB。

### 7.2 状态规则

- 正式产物不可原地覆盖，只能创建新版本。
- 草稿可以覆盖，但必须记录最后编辑时间和作者。
- 新版本提交后，根据 operation 的 `invalidates` 标记下游产物过期。
- 过期不等于删除，历史版本仍可查看和恢复。
- 质量/合规报告必须绑定明确的剧本版本和集数范围。
- 修订只能使用用户明确接受的问题。
- 交付只能读取当前有效且通过门禁的版本。

### 7.3 API 分区

- `/api/v2/projects/`：项目列表、创建、归档。
- `/api/v2/projects/{id}/overview/`：业务阶段、下一步、待处理事项。
- `/api/v2/projects/{id}/brief/`：创作定位读写与生成。
- `/api/v2/projects/{id}/bible/`：故事设定聚合视图。
- `/api/v2/projects/{id}/characters/`：人物视图和人工草稿编辑。
- `/api/v2/projects/{id}/episode-plan/`：分集规划、范围修订、分析视图。
- `/api/v2/projects/{id}/scripts/`：集/场景树、正文草稿、版本。
- `/api/v2/projects/{id}/reviews/`：质量、合规、问题接受和复核。
- `/api/v2/projects/{id}/delivery/`：门禁、生成和下载。
- `/api/v2/runs/{id}/`：运行摘要。
- `/api/v2/runs/{id}/evidence/`：完整八阶段和 LLM 证据。
- `/api/v2/analytics/`：仅第三阶段开放。

所有写 API 使用幂等 command ID 和 `If-Match`/base version 防止覆盖并发版本。

## 8. 前端架构

- React + Vite + TypeScript。
- React Router：全局路由和项目内嵌套路由。
- TanStack Query：服务端状态、运行轮询和缓存失效。
- Tailwind + 小型本地设计系统：按钮、输入、标签、抽屉、对话框、空状态、骨架屏。
- Tiptap：结构化剧本编辑器和选区 AI 操作。
- ECharts：情绪曲线、钩子分布和第三阶段分析。
- Zod：API 响应和编辑器文档结构的运行时校验。

前端目录按业务域划分：`projects`、`brief`、`bible`、`planning`、`editor`、`review`、`delivery`、`runs`、`analytics`。删除以旧页面名称和后台工具名称组织的目录。

## 9. 三阶段开发计划

### 第一阶段：核心创作闭环

目标：单人用户可以从创意走到一批可编辑的分集剧本。

#### 功能范围

- 新版全局壳层和项目列表。
- 引导式新建项目。
- 项目概览与业务阶段状态。
- 创作定位候选、编辑、确认和版本。
- 故事设定聚合页：人物、世界、关系、情绪、原创性。
- 分集规划卡片/表格和局部调整。
- Tiptap 剧本编辑器、分集/场景导航、自动保存。
- 批量写作、候选 diff、确认提交。
- 版本历史、过期标记和运行详情。
- 所有 LLM 调用完整追踪。

#### 后端交付

- 新领域模型与迁移。
- Artifact repository、operation orchestrator、candidate/commit service。
- V6 runtime adapter，不保留 V5 业务服务入口。
- 项目、brief、bible、plan、script、run API。
- Celery 任务、取消、重试和幂等。

#### 验收标准

- 原创和改编项目都能完成建项。
- 五组故事设定产物可原子提交。
- 分集计划可以只修改指定集数并正确显示影响范围。
- 可以批量生成指定集数，连续性检查点被持久化。
- AI 结果不会未经确认覆盖正文。
- 任意正式产物都能追溯到 operation run 和 LLM calls。
- 页面不出现 operation ID、artifact key 等内部术语。

### 第二阶段：质量、修订与交付闭环

目标：把已写剧本审到可交付，并支持外部剧本独立审稿。

#### 功能范围

- 项目审稿中心。
- 质量评分与合规检查双通道。
- 问题证据定位、接受/忽略和批量选择。
- 基于已接受问题的定向修订。
- 修订前后正文差异和影响范围。
- 复核状态与报告过期处理。
- 制作交付门禁、制作可行性、预算摘要和交付包。
- Word/PDF/结构化数据导出。
- 独立审稿入口，结果使用同一套报告组件和运行证据。

#### 后端交付

- QualityFinding 标准化服务。
- score/compliance 并行编排和按 script version join。
- revision acceptance contract。
- delivery readiness gate 与 ExportPackage。
- 文件导出任务和安全下载。

#### 验收标准

- 两份报告必须绑定相同剧本版本才能形成联合结论。
- 用户未接受的问题不能进入自动修订。
- 修订仅改选定集数，并加载相邻集上下文。
- 正文变化后旧报告立即标记为过期。
- 未通过质量或合规门禁时无法生成正式交付包。
- 独立审稿和项目审稿都可完整追溯。

### 第三阶段：数据看板与创作分析

目标：用真实使用数据帮助创作者发现效率、质量和结构问题。第三阶段只做以下两类功能。

#### A. 数据看板

- 项目总量、完成项目、进行中项目。
- 本周/本月创作集数、有效字数、完成场景数。
- AI 运行次数、成功率、平均耗时、token/成本估算。
- 从建项到首集、从首集到交付的周期。
- 各创作阶段耗时和阻塞分布。
- 质量初审通过率、合规通过率、平均修订轮次。

#### B. 创作分析

- 全剧情绪曲线和分集偏离提示。
- 钩子密度、结尾钩子类型、付费点分布。
- 伏笔埋设/回收覆盖率和未回收清单。
- 人物出场、关系变化、角色弧推进和人物失焦提示。
- 场景数量、场景复用率、制作复杂度和预算趋势。
- 对白/动作占比、单集字数、节奏异常集数。
- 质量维度趋势、反复出现的问题和修订收益。
- 合规风险类型趋势，不展示没有证据的推测性评分。

#### 数据基础

- 第一阶段即定义并采集 `UsageEvent`，但不提前开发看板。
- 分析指标优先从 V6 结构化产物计算，不用 LLM 二次猜测已有字段。
- 每个指标可以下钻到项目、版本、集数、场景和证据。
- 看板不包含会员收入、用户增长、团队协作或交易数据。

#### 验收标准

- 指标口径有定义、时间范围和数据来源。
- 汇总数可以下钻并与原始产物/事件对账。
- 分析结果明确区分“结构化计算”和“AI 判断”。
- 数据不足时显示缺失原因，不生成虚假趋势。

## 10. 测试策略

### 后端

- V6 operation contract 和 schema 测试。
- 版本提交、并发冲突、幂等和 invalidation 测试。
- 多产物原子提交回滚测试。
- 质量/合规按版本 join 测试。
- 接受问题后修订的范围和保留项测试。
- 交付门禁测试。
- LLM 调用失败、重试、超时和取消测试。
- Analytics 指标口径测试。

### 前端

- 页面路由与权限测试。
- 新建项目向导条件字段测试。
- 编辑器文档节点和自动保存测试。
- 候选 diff、接受、拒绝和版本冲突测试。
- 审稿问题定位和批量修订测试。
- 空、加载、失败、过期、无权限状态测试。
- 1280/1440 桌面和 390 移动端视觉回归；编辑器重点验证桌面。

### 端到端

至少覆盖：

1. 原创项目 -> 定位 -> 设定 -> 规划 -> 写 1-3 集。
2. 改编项目 -> 锁定保留项 -> 生成设定 -> 局部修改分集。
3. 写作 -> 双报告 -> 接受问题 -> 修订 -> 复核 -> 交付。
4. 任意任务失败 -> 查看原因 -> 修改输入 -> 重试成功。
5. 从最终剧本版本追溯到全部 LLM 调用证据。

## 11. 实施顺序与里程碑

1. **M0 产品基线**：确认信息架构、页面线框、术语表和 V6 映射。
2. **M1 领域底座**：新模型、迁移、artifact repository、operation orchestrator。
3. **M2 项目与定位**：项目列表、建项向导、项目简报完整链路。
4. **M3 故事设定**：故事蓝图和人物/世界/情绪视图。
5. **M4 分集规划**：全剧计划、局部调整、影响预览。
6. **M5 剧本编辑器**：结构化正文、自动保存、批量写作、候选提交。
7. **M6 质量闭环**：评分、合规、问题接受、定向修订、复核。
8. **M7 制作交付**：门禁、交付包、导出。
9. **M8 稳定化**：全链路追踪、错误恢复、性能、安全和视觉回归。
10. **M9 第三阶段**：数据看板和创作分析。

每个里程碑必须同时交付 API、页面、自动化测试、空/错/加载状态和数据迁移，不以静态页面完成作为验收。

## 12. 开工前必须确认的设计产物

- 全局和项目内信息架构图。
- 六个核心页面线框：项目列表、项目概览、故事设定、分集规划、剧本编辑器、审稿修订。
- 剧本编辑器节点模型和交互规范。
- 候选/版本/diff/过期的统一交互规范。
- 质量问题证据定位规范。
- 用户术语到 V6 operation/artifact 的映射表。
- 第三阶段指标字典和第一阶段埋点表。

以上设计确认后再开始大规模改代码，避免再次用内部架构替代产品设计。
