# Fullstack Refactor Plan

## 适用场景

当用户提出以下需求时使用本技能：

- 为 Django + DRF 后端和 React SPA 前端制定重构落地方案。
- 解决目录层级混乱、业务模块耦合、接口命名不统一、状态管理混乱、重复代码多等可维护性问题。
- 设计 RESTful 接口规范、统一响应体、错误码体系、跨域、鉴权、请求拦截、全局异常处理。
- 规划前端目录分层、组件拆分、自定义 Hooks、Axios 封装、路由懒加载、权限守卫和状态管理边界。
- 规划后端业务 app 拆分、View/ViewSet、Serializer、Model、Service、utils、异常中间件和 DRF 通用能力。
- 需要渐进式重构步骤、数据安全方案、回归测试方案、版本备份和风险控制。
- 后续逐个粘贴代码文件，要求按既定架构规范重构并说明修改点。

## 项目基础信息

- 后端默认按 Django + Django REST Framework 处理。
- 前端默认按 React SPA 处理；如项目已使用 TypeScript、React Query、Zustand、Redux、TailwindCSS、Axios 等，优先对齐现有依赖。
- 禁止为了重构方案随意引入新第三方库；确需引入时必须说明理由、替代方案和迁移成本。
- 输出默认使用中文；代码、接口路径、目录名、字段名保持英文规范。

## 工作原则

1. 先识别现有目录、路由、接口、状态、模型和核心业务调用链，再给方案。
2. 优先渐进式重构，不建议一次性大改；每一步都应保证项目可运行、可回滚。
3. 接口契约变更必须明确前后端影响，避免私自修改字段语义和返回结构。
4. 后端业务逻辑下沉到 `services.py` 或领域服务层，Serializer 只做序列化和校验，View/ViewSet 只做编排。
5. 前端请求统一进入 `services` 或 `api` 层，组件禁止散落拼接接口路径和重复处理 token、错误提示。
6. 状态按作用域分层：服务端状态、全局客户端状态、页面局部状态、表单临时状态分别治理。
7. 数据库重构必须先做备份、迁移脚本、回滚策略和灰度验证；禁止直接修改生产表结构。
8. 风险控制优先级：正确性、数据安全、向后兼容、可维护性、性能、设计优雅。
9. 逐文件代码改造默认禁止改动原有业务逻辑、禁止修改数据库表结构、禁止修改对外接口 URL。

## 输出要求

当用户要“方案”时，按四阶段输出：

1. 架构规范设计：后端 app 与分层、前端 `src` 目录、RESTful 接口、统一响应、异常、错误码、JWT 鉴权。
2. 渐进式重构步骤：低风险顺序、每步验证方案、回滚策略。
3. 代码改造规则：逐文件重构流程、修改说明模板、禁止变更边界。
4. 后期维护方案：代码约束、自测方案、规避再次结构混乱的建议。

当用户要“实现代码”时：

1. 先读取现有项目结构、核心路由、请求封装、异常处理、权限和状态管理实现。
2. 给出小步改造计划，优先补齐基础框架和兼容层。
3. 每次只改一类问题，例如请求封装、路由组织、单个业务 app 的 service 抽取。
4. 如果用户粘贴单个文件，先分析调用链和职责归属，再重构为更清晰的组件、Hook、service、selector 或工具函数。
5. 修改后说明“保持不变的业务行为”和“实际调整点”；运行或说明关联测试。
6. 涉及数据库迁移、接口 URL、响应字段语义变化时，先暂停并向用户确认。
