# 前后端分离项目重构落地方案模板

## 使用方式

当用户要求主导 Django + DRF 后端和 React 前端重构时，先按四阶段给出方案：

1. 架构规范设计。
2. 渐进式重构步骤。
3. 代码改造规则。
4. 后期维护方案。

如果用户后续逐个粘贴代码文件，默认按“只改结构和可维护性，不改业务行为”的原则执行。除非用户明确授权，禁止修改数据库表结构、对外接口 URL、接口字段语义和核心业务流程。

## 第一阶段：架构规范设计

### 1. RESTful 接口设计规范

统一接口前缀：

```text
/api/v1/{resource}/
/api/v1/{resource}/{id}/
/api/v1/{resource}/{id}/{action}/
```

请求方式：

- `GET`：查询列表或详情，不修改数据。
- `POST`：创建资源或执行非幂等业务动作。
- `PUT`：全量更新。
- `PATCH`：局部更新。
- `DELETE`：删除或软删除，高风险操作必须鉴权、审计和二次确认。

命名规范：

- 资源名使用复数名词，例如 `/api/v1/projects/`、`/api/v1/orders/`。
- 项目内统一使用 kebab-case 或 snake_case；推荐 kebab-case。
- 查询、筛选、分页、排序放入 query，例如 `?status=active&page=1&page_size=20&ordering=-created_at`。
- 避免 `/getUserList`、`/deleteOrder` 这类动词式路径。

统一成功响应：

```json
{
  "code": 0,
  "message": "success",
  "data": {}
}
```

统一分页响应：

```json
{
  "code": 0,
  "message": "success",
  "data": {
    "count": 100,
    "page": 1,
    "page_size": 20,
    "results": []
  }
}
```

统一错误响应：

```json
{
  "code": 40001,
  "message": "参数校验失败",
  "data": {
    "field_errors": {
      "name": ["该字段不能为空"]
    }
  }
}
```

错误码建议：

- `0`：成功。
- `400xx`：参数错误、非法状态、重复提交。
- `401xx`：未登录、token 失效、登录态异常。
- `403xx`：无权限、账号禁用、资源不可访问。
- `404xx`：资源不存在。
- `409xx`：资源冲突、并发版本冲突。
- `429xx`：请求过于频繁。
- `500xx`：系统异常、外部依赖异常、任务执行失败。

### 2. 跨域、鉴权、请求拦截、全局异常

跨域：

- 后端统一配置 CORS，只允许可信前端域名。
- 生产环境禁止 `CORS_ALLOW_ALL_ORIGINS=True`。
- Cookie 鉴权必须配置 `SameSite`、`Secure`、CSRF 和可信域名。

鉴权：

- 后端统一使用 DRF authentication 和 permission classes。
- 前端请求层统一注入 token，组件层不直接拼接鉴权头。
- token 过期走统一刷新或退出登录流程。
- 前端权限守卫只优化体验，真实权限以后端为准。

请求拦截：

- 前端建立全局请求实例，统一 `baseURL`、超时、token、错误码映射。
- 响应拦截负责解包、登录态失效、网络异常、超时和通用提示。
- 拦截器不要吞掉所有业务错误，页面仍可按业务语义处理异常。

全局异常：

- 后端通过 DRF 自定义 exception handler 标准化响应体。
- 参数校验、认证、权限、业务异常、系统异常必须区分。
- 系统异常只返回通用提示，不暴露堆栈、SQL 或内部路径。
- 日志记录 request id、用户 id、接口路径、耗时、错误上下文和堆栈。

## 二、前端 React 标准化目录重构方案

### 1. 推荐目录结构

```text
src/
├── app/
│   ├── App.jsx
│   ├── providers/
│   └── router/
├── pages/
├── components/
│   ├── common/
│   └── layout/
├── features/
│   └── project/
│       ├── components/
│       ├── hooks/
│       ├── services/
│       ├── stores/
│       ├── types/
│       └── utils/
├── hooks/
├── services/
│   ├── http/
│   └── modules/
├── stores/
├── types/
├── utils/
├── constants/
├── styles/
└── assets/
```

职责：

- `app`：应用入口、Provider、路由注册。
- `pages`：页面级容器，只组合布局和业务模块。
- `components/common`：跨业务纯 UI 组件。
- `components/layout`：布局、导航、侧边栏、权限外壳。
- `features`：按业务领域聚合组件、Hooks、接口、状态、类型和工具。
- `hooks`：跨业务复用 Hooks。
- `services/http`：请求实例、拦截器、错误处理、token 注入。
- `services/modules`：跨业务 API 模块。
- `stores`：全局客户端状态。
- `types`：全局类型；业务类型优先放在对应 `features`。
- `utils`：纯函数工具，不依赖 React 和业务状态。
- `constants`：枚举、常量、配置键。

### 2. 组件拆分原则

公共组件：

- 不包含具体业务请求。
- 不依赖某个页面的数据结构。
- 通过 props 和事件回调通信。
- 放入 `components/common`。

业务组件：

- 服务于明确业务域，例如项目、订单、会员、创作。
- 可依赖业务类型、业务 Hooks 和业务服务。
- 放入 `features/{domain}/components`。

拆分策略：

- 页面文件过长时，拆出布局区块、列表区块、表单区块、弹窗区块。
- 重复 UI 拆组件，重复副作用或数据流程拆 Hook。
- 重复数据转换拆到 `utils` 或业务 service。
- 表单校验、弹窗控制、分页查询、上传流程优先抽为 `useXxx`。

### 3. 状态管理梳理

状态分类：

- 服务端状态：列表、详情、搜索结果、分页结果，优先交给 React Query、SWR 或现有缓存方案。
- 全局客户端状态：登录用户、主题、语言、全局配置、权限、布局状态。
- 页面局部状态：筛选条件、弹窗开关、当前 tab、临时选中项。
- 表单状态：表单库或组件局部 state 管理，不进入全局 store。

清理原则：

- 能从 props 推导的值不单独存 state。
- 能从 URL query 表达的筛选条件优先同步到 URL。
- 服务端返回的权威状态不在前端重复维护副本。
- 只被单个组件使用的状态不放入全局 store。

### 4. Axios 请求封装整改

推荐结构：

```text
src/services/http/
├── client.js
├── errorCodes.js
├── token.js
└── types.js
```

职责：

- `client.js`：创建 Axios 实例，注册请求和响应拦截器。
- `token.js`：读取、写入、清理 token。
- `errorCodes.js`：错误码映射和用户提示。
- 业务 API 文件只声明接口函数，例如 `getProjectList(params)`、`createProject(payload)`。

禁止项：

- 组件内直接调用裸 `axios`。
- 组件内重复拼接 `baseURL`。
- 每个接口重复写 token header。
- 页面重复解包统一响应体。

### 5. 路由懒加载与权限守卫

推荐结构：

```text
src/app/router/
├── index.jsx
├── routes.jsx
├── guards.jsx
└── lazyLoad.jsx
```

规范：

- 页面路由默认懒加载，统一 `Suspense` loading。
- 路由配置集中管理。
- 路由元信息包含 `title`、`requiresAuth`、`permissions`、`layout`。
- 权限守卫负责跳转和可见性，后端负责真实权限校验。
- 404、403、登录页、主布局和业务路由分层清晰。

## 三、后端 Django 标准化目录重构方案

### 1. 项目根目录与业务 app 拆分

推荐结构：

```text
backend/
├── config/
│   ├── settings/
│   ├── urls.py
│   ├── asgi.py
│   └── wsgi.py
├── apps/
│   ├── accounts/
│   ├── projects/
│   ├── orders/
│   ├── membership/
│   └── system_config/
├── common/
│   ├── exceptions.py
│   ├── pagination.py
│   ├── permissions.py
│   ├── responses.py
│   ├── serializers.py
│   ├── services.py
│   └── utils/
├── manage.py
└── requirements.txt
```

app 拆分原则：

- 按业务领域拆分，不按技术层拆分。
- 单个 app 只承载单一业务边界。
- 跨 app 调用通过 service 或领域接口完成，避免循环导入。
- 公共能力放入 `common`，不要塞进任意业务 app。

### 2. 分层设计

单个业务 app 推荐结构：

```text
apps/projects/
├── models.py
├── serializers.py
├── views.py
├── urls.py
├── services.py
├── permissions.py
├── selectors.py
├── filters.py
├── tasks.py
├── admin.py
└── migrations/
```

职责：

- `models.py`：数据结构、枚举、约束、索引；建议显式 `db_table`。
- `serializers.py`：序列化、反序列化、参数校验；不写业务流程。
- `views.py`：DRF ViewSet/APIView，只做鉴权、参数接收、调用 service、返回响应。
- `services.py`：核心业务逻辑、事务、跨模型写入、领域规则。
- `selectors.py`：复杂查询和读取聚合，统一处理 `select_related`、`prefetch_related`。
- `permissions.py`：权限类，不在视图里硬编码权限判断。
- `filters.py`：过滤、搜索、排序规则。
- `tasks.py`：耗时异步任务，避免阻塞请求线程。

异常与响应：

- `common/exceptions.py` 定义业务异常和错误码。
- `common/responses.py` 定义统一响应结构。
- `common/exception_handler.py` 接入 DRF `EXCEPTION_HANDLER`。
- 日志不记录敏感字段，不向前端暴露系统错误细节。

### 3. 模型与字段优化建议

模型治理：

- 删除无用字段前先统计读写路径和数据使用情况。
- 枚举统一使用 `models.TextChoices` 或 `models.IntegerChoices`。
- 高频查询字段按实际查询建立索引，避免滥用索引。
- 多字段唯一性使用数据库约束兜底，避免仅靠代码判断。
- 软删除、状态流转、审计字段在项目内统一。

外键治理：

- 外键命名必须表达业务语义，避免 `obj`、`ref`、`data`。
- 明确 `on_delete` 策略；核心业务数据避免误级联删除。
- 多表查询必须治理 N+1，使用 `select_related` 或 `prefetch_related`。

数据模型分层：

- Model 表达存储结构和基础约束。
- Serializer 表达接口输入输出结构。
- Service 表达业务规则。
- Selector 表达复杂读取视图。
- 前端 Type 类型来自接口契约，不反向绑死数据库字段。

### 4. DRF 接口统一封装

基础能力：

- 统一分页类：默认页码、最大 `page_size`、统一分页响应。
- 统一过滤：使用项目既有过滤方案，集中定义字段白名单。
- 统一权限：登录、管理员、资源所有者、只读等权限类。
- 统一响应：所有接口返回 `{ code, message, data }`。
- 统一异常：业务异常、校验异常、认证权限异常、系统异常分层处理。

ViewSet 约束：

- `get_queryset` 只返回可访问数据范围。
- `get_serializer_class` 可按 action 切换输入输出 Serializer。
- 创建、更新、删除等写操作调用 service，并在 service 内处理事务。
- 列表接口默认具备分页、过滤、搜索、排序能力。

### 5. 数据库迁移与数据安全

迁移原则：

- 禁止直接手动改生产表结构。
- 结构迁移和数据迁移拆分，降低回滚难度。
- 字段重命名采用“新增字段、双写、回填、切读、清理旧字段”的方式。
- 删除字段前至少经过确认、备份、灰度和观测。
- 大表迁移分批执行，避免长事务和锁表。

数据安全：

- 迁移前导出备份，记录备份位置和恢复步骤。
- 数据迁移脚本必须可重复执行，使用幂等逻辑。
- 核心写操作使用 `transaction.atomic`。
- 高风险迁移先在测试库或预发环境演练。

## 第二阶段：渐进式重构步骤

### 第一步：搭建基础规范框架

目标：

- 新增统一响应、错误码、全局异常、分页、权限基类。
- 前端新增统一请求实例和错误处理。
- 梳理路由入口和 API 模块入口。

验收：

- 旧接口仍可访问。
- 新增规范能力有最小示例接口验证。
- 前端请求统一入口可正常处理成功、失败、登录失效。

回滚：

- 保留旧响应和旧请求封装，新增统一封装先只接入示例接口。
- 前端可通过模块级导入回退到旧请求函数。
- 后端可临时关闭自定义异常处理，恢复 DRF 默认处理。

### 第二步：接口规范化整改

目标：

- 按业务域梳理接口清单、命名、请求方式、入参、返回体。
- 优先整改高频和新开发接口，旧接口保留兼容层。
- 统一分页、过滤、排序和错误响应。

验收：

- 每个接口有明确契约。
- 前后端字段命名和类型一致。
- 旧页面不因响应结构调整而崩溃。

回滚：

- 不删除旧接口 URL，必要时新增兼容 adapter。
- 响应结构调整先在前端请求层兼容，失败时切回旧解包逻辑。
- 每个接口整改独立提交，避免批量回滚困难。

### 第三步：前端页面和组件逐步拆分

目标：

- 从最大、最混乱、变化最高的页面开始。
- 每次只拆一个页面或一个业务域。
- 页面拆为容器、业务组件、公共组件、Hooks、services。

验收：

- 拆分前后功能等价。
- 页面 state 数量减少，重复请求逻辑收敛到 services/Hooks。
- 路由懒加载和权限守卫正常。

回滚：

- 保留原页面入口，新组件先由原页面组合引用。
- 拆分失败时恢复单页面容器，不影响路由和接口。
- 公共组件抽取必须先确认至少两个真实复用点，避免提前抽象。

### 第四步：后端业务逻辑解耦和 Service 层抽取

目标：

- 将 View/ViewSet 中的业务流程迁移到 service。
- 将复杂读取迁移到 selector。
- 跨模型写入统一加事务。
- 治理 N+1 查询和重复查询。

验收：

- View/ViewSet 只负责编排。
- Service 可单元测试。
- 核心业务路径有事务和权限兜底。

回滚：

- View/ViewSet 调用 service 前保持原参数和返回结构不变。
- service 抽取应先迁移代码位置，再做小范围可读性整理。
- 如果事务或查询优化引入异常，回退到原查询路径并保留测试用例。

### 第五步：全局优化和测试补充

目标：

- 清理废弃接口、重复组件、无用状态和旧工具函数。
- 补充单元测试、接口测试、关键页面回归测试。
- 梳理技术债列表，保留无法立即处理的问题。

验收：

- 关键测试通过。
- 构建通过。
- 重构后的目录和规范写入项目规则或 README。

回滚：

- 废弃代码清理必须放在最后，先标记后删除。
- 删除前确认无路由、导入、任务、模板、脚本引用。
- 发现遗漏引用时恢复旧文件，再补充替换清单。

## 第三阶段：代码改造规则

### 1. 单文件重构流程

每次用户粘贴或指定一个文件时，按以下顺序处理：

1. 判断文件职责：页面、组件、Hook、API service、Django View、Serializer、Service、Model、Task、工具函数。
2. 梳理调用链：入口、外部依赖、被谁调用、接口 URL、数据库读写、状态流向。
3. 标注不可变边界：业务逻辑、数据库表结构、对外接口 URL、字段语义、权限语义。
4. 提出最小改造计划：拆分目标、迁移路径、测试点。
5. 执行代码修改：只做职责拆分、重复收敛、命名整理、错误处理统一和可测试性增强。
6. 输出修改说明：根因、修改点、保持不变的行为、验证方式。

### 2. 后端文件改造规则

- `models.py`：默认不改字段、表名、约束和迁移；只在用户确认后处理数据库结构。
- `serializers.py`：只做入参校验和序列化，不塞业务流程；敏感字段必须 `write_only=True` 或不返回。
- `views.py` / `viewsets.py`：瘦身为鉴权、参数接收、调用 service、返回响应。
- `services.py`：承载核心业务逻辑；多表写入使用 `transaction.atomic`。
- `selectors.py`：承载复杂读取；治理 N+1 时使用 `select_related` / `prefetch_related`。
- `tasks.py`：耗时逻辑保持异步，不把 Celery 任务改成同步请求逻辑。
- `utils.py`：只放无副作用通用函数，不放业务流程。

### 3. 前端文件改造规则

- 页面文件：保留路由入口职责，拆出业务组件、弹窗、表单、列表、空状态和加载状态。
- 业务组件：放到 `features/{domain}/components`，通过 props 和事件回调通信。
- 自定义 Hook：抽离请求编排、分页、筛选、弹窗、上传、表单副作用，命名以 `use` 开头。
- API 请求：统一放到 `services`、`api` 或 `features/{domain}/services`，组件禁止裸调用 `fetch` / `axios`。
- 状态管理：服务端状态、全局状态、页面局部状态、表单状态分开治理。
- 工具函数：保持纯函数，避免依赖 React state、DOM 和业务请求。

### 4. 修改说明模板

```markdown
根因：
- [说明文件当前维护问题，例如职责混杂、重复请求、业务逻辑堆在视图中]

修改点：
- [列出实际改动，聚焦结构和职责]

保持不变：
- 业务逻辑不变。
- 数据库表结构不变。
- 对外接口 URL 不变。
- 字段语义和权限语义不变。

验证：
- [列出需要运行的测试、页面回归或接口验证]
```

## 第四阶段：后期维护方案

### 1. 避免 Bug

- 小步提交，每次只改一个明确范围。
- 改前梳理调用链、接口契约、数据读写路径。
- 保留旧接口或兼容适配层，等新逻辑稳定后再清理。
- 核心路径补充测试，至少覆盖正常、边界、异常、权限、并发或重复提交场景。
- 重构不夹带业务需求变更。

### 2. 代码约束

- 新功能必须先确定业务域归属，再新增 app、feature、service 或组件。
- 后端 View/ViewSet 不写核心业务流程，前端页面不直接写复杂请求编排。
- 新接口必须统一响应结构、错误码、分页、认证和权限。
- 新增公共组件前确认跨业务复用价值；业务组件优先留在对应 feature。
- 大文件达到明显臃肿时及时拆分，避免单文件继续堆逻辑。
- 禁止在组件、视图、任务中复制粘贴相同业务规则。

### 3. 版本备份

- 每个阶段开始前创建独立分支。
- 大范围调整前打 tag 或记录可回退 commit。
- 数据库迁移前备份数据库。
- 重要配置和环境变量变更单独记录。

### 4. 分步自测验证

前端：

- 登录、退出、token 失效。
- 核心页面列表、详情、创建、编辑、删除。
- 路由刷新、无权限访问、404。
- 网络异常、接口业务错误、表单校验错误。

后端：

- 接口成功响应格式。
- 参数校验错误格式。
- 认证和权限错误格式。
- 分页、过滤、排序。
- Service 事务回滚。
- 数据迁移前后数据量、关键字段、外键关系一致。

发布：

- 先测试环境验证，再预发回归，再生产灰度。
- 生产发布后观察错误日志、接口耗时、关键业务指标。
- 出现异常时按预案回滚代码或切回旧接口。

### 5. 防止再次混乱

- 将目录规范、接口规范和异常响应写入项目规则或开发文档。
- PR 检查必须包含目录归属、接口契约、权限、测试和回滚影响。
- 每个迭代预留技术债清理时间，避免重构只做一半。
- 定期扫描超长文件、重复请求、裸接口调用、未分页列表和视图业务逻辑。
