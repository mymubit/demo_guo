# Fullstack Cleanup Audit

## 项目基础信息

前后端分离项目，后端 Django+DRF，前端 React。

现存问题：

1. 存在大量历史遗留废弃文件、过期配置、测试残留文件、重复冗余文件，长期未清理；
2. 部分业务代码放置模块不合理（本该抽离工具层/服务层的代码，混杂在视图/页面组件里）；
3. 文件、变量、函数、组件命名不统一，命名风格混乱，可读性差；
4. 目录模块划分不合理，职责边界模糊。

## 适用场景

当用户提出以下需求时使用本技能：

- 梳理「可直接删除 / 需要移动 / 需要重命名 / 配置优化」四类清单。
- 制定安全、可回滚的清理与归类执行步骤。
- 制定前端 React、后端 Django 的长期命名与目录规约。
- 在不改业务逻辑、不改数据库结构、不改对外接口地址的前提下做代码卫生整理。

与 [fullstack-refactor-plan](../fullstack-refactor-plan/SKILL.md) 的分工：

- **本技能**：存量盘点、删除/迁移/重命名、配置精简、安全执行与回滚。
- **fullstack-refactor-plan**：架构分层、接口规范、Service 抽取、渐进式重构方案。

## 硬性约束

① 不能修改现有业务逻辑、不能改动数据库结构、不能修改对外接口地址；

② 所有删除、移动操作必须标注风险等级，高危删除必须二次确认；

③ 改动后必须保证项目可正常启动、原有功能完全可用。

## 分析前置步骤

开始输出清单前，必须先读取实际项目结构，禁止凭猜测列文件：

1. 定位主应用根目录（如 `ScriptForge/backend`、`ScriptForge/frontend`）。
2. 读取路由入口：`config/urls.py`、`apps/*/urls.py`、前端 `router`/`App` 配置。
3. 读取依赖声明：`requirements*.txt`、`pyproject.toml`、`package.json`。
4. 读取构建/部署配置：`vite.config.*`、`webpack.config.*`、`docker-compose*`、`.env.example`。
5. 对候选废弃项做引用扫描（import、URL 注册、动态 import、模板引用、CI 脚本引用）。
6. 若用户提供目录结构附件，以其为起点交叉验证，但以仓库实际引用为准。

引用扫描命令参考见 [REFERENCE.md](REFERENCE.md#引用扫描方法)。

## 输出要求

按以下四段结构输出，每段使用表格，列必须完整：

### 1. 分类梳理清单

#### 【可直接安全删除】

| 路径 | 类型 | 风险等级 | 删除理由 | 引用扫描结果 |
|------|------|----------|----------|--------------|

类型：`废弃文件` / `旧配置` / `临时文件` / `过期脚本` / `无用依赖` / `注释死代码`

#### 【需要移动归类】

| 原路径 | 目标路径 | 风险等级 | 归类逻辑 | 需同步更新的引用 |
|--------|----------|----------|----------|------------------|

#### 【需要重命名】

| 范围 | 原名 | 规范名称 | 风险等级 | 命名依据 |
|------|------|----------|----------|----------|

范围：`文件` / `目录` / `变量` / `函数` / `组件`

#### 【仅保留+优化】

| 配置文件 | 保留理由 | 可删除/合并项 | 精简建议 |
|----------|----------|---------------|----------|

### 2. 输出执行步骤

严格按以下顺序分步，每步附带校验方法与回滚点：

```
Phase 0: 先核对确认
Phase 1: 小批量删除
Phase 2: 迁移归类
Phase 3: 统一重命名
Phase 4: 逐轮自测
```

各 Phase 的详细 checklist 与命令见 [REFERENCE.md](REFERENCE.md#分步执行与校验)。

### 3. 制定长期命名 & 目录规约

分别输出前端 React、后端 Django 的：

- 文件命名规范
- 文件夹命名规范
- 变量 / 函数 / 组件 / 类 / 模块统一规范

完整规约模板见 [REFERENCE.md](REFERENCE.md#长期命名与目录规约)。

## 风险等级定义

| 等级 | 含义 | 操作要求 |
|------|------|----------|
| 🟢 低 | 构建产物、缓存、日志、明确零引用 | 可直接执行，记录 commit |
| 🟡 中 | 疑似废弃但可能有动态引用 | 小批量 + 引用扫描 + 自测 |
| 🔴 高 | 路由/模型/迁移/环境配置/共享模块 | **必须二次确认**，禁止批量 |

高危删除二次确认模板：

```markdown
⚠️ 高危删除待确认
- 路径：...
- 风险：...
- 扫描结果：...
- 请确认是否删除？(yes/no)
```

## 执行原则

1. **先清单后动手**：未输出完整四类清单前，不执行删除或移动。
2. **小步提交**：每 Phase 独立分支或 commit，便于 `git revert`。
3. **移动优先于重命名**：先归位再统一命名，减少 import 震荡。
4. **重命名用 IDE/工具批量替换**：改完立即跑 lint、build、test。
5. **配置只删不生效项**：删前 diff 运行环境实际读取的配置键。
6. **禁止夹带业务变更**：清理 PR 不含功能改动；逻辑下沉单独 PR。

## 当用户要求「直接执行清理」时

1. 先完成 Phase 0 核对，获得用户对 🔴 项的明确确认。
2. 每次只处理同一风险等级、同一类型的一批文件（建议 ≤10 个）。
3. 执行后立即运行该 Phase 校验命令；失败则回滚当前批次。
4. 全部 Phase 完成后输出变更摘要与剩余待办。
