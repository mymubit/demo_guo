# Dynamic System Config

## 项目基础信息

- 后端：Django + Django REST Framework。
- 前端：React + TailwindCSS + clsx + tailwind-merge + lucide-react + framer-motion + sonner + echarts-for-react。
- 优先复用项目已有服务层、权限类、请求封装、基础组件、全局状态和缓存工具。
- 禁止为配置中心随意引入新第三方库；确需新增依赖时必须说明理由和替代方案。

## 适用场景

当用户提出以下需求时使用本技能：

- 将前端 `const`、后端常量文件、业务阈值、枚举、文案、开关配置迁移到数据库。
- 设计或实现“动态配置中心”“系统配置后台”“配置管理后台”。
- 为 Django + DRF 后端和 React + Tailwind 前端补充配置表、接口、缓存、Hook、页面或迁移脚本。
- 要求低风险灰度迁移、缓存兜底、管理员权限控制、配置修改日志或新旧逻辑并行。

与其他技能分工：

- **本技能**：配置表、接口、缓存、管理页、硬编码迁移
- [fullstack-release-deploy](../fullstack-release-deploy/SKILL.md)：配置变更的生产发布与回滚
- [fullstack-testing](../fullstack-testing/SKILL.md)：配置读写与灰度场景测试

## 工作原则

1. 先扫描现有配置来源、调用链和管理后台结构，再设计迁移范围。
2. 后端以独立 `system_config` APP 承载配置模型、接口、缓存和服务层。
3. 业务代码读取统一通过 `get_config(key, default_val)` 或等价服务入口，避免散落查库逻辑。
4. 写入配置必须刷新缓存；读取优先缓存，Redis 优先，无 Redis 时使用进程内缓存兜底。
5. 配置修改仅管理员可执行；普通账号只读或按现有权限体系限制。
6. 前端默认值不得在组件内随意兜底；默认值来源应由后端配置或统一配置工具管理。
7. 迁移必须支持新旧并行与快速回退，避免一次性替换全部硬编码。
8. 敏感配置与普通业务配置分级处理，敏感值默认不下发前端，不在日志中明文输出。

## 输出要求

当用户要“方案”时，按以下结构输出：

1. 后端 Django 设计：表结构、APP 分层、接口全集、缓存、工具函数、权限、迁移脚本。
2. 前端改造设计：API 封装、初始化、`useConfig`、后台页面、存量替换示例。
3. 分步迁移步骤：建表、导入、页面、灰度替换、回归测试、清理旧文件。
4. 约束与规范：兼容回退、敏感配置、默认值策略、后续新增配置流程。

当用户要“实现代码”时：

1. 先定位现有 Django APP、路由、权限、缓存、前端请求层和后台页面风格。
2. 给出小步计划，优先实现后端模型、服务、缓存、接口和迁移。
3. 再实现前端 API、配置状态、Hook、管理页面。
4. 补充迁移脚本模板和关键测试。
5. 每一步完成后运行或说明关联测试。
